How RiftCluster works

Three copies of one mock server, behind a load balancer, that behave like one. This page builds the design up from the obvious approach, shows where it breaks, and lets you drive each mechanism yourself: elect a leader, commit a write, move a flow between owners, crash the fleet mid-fsync.

1 · One node, and what it can't do

Rift is a Mountebank-compatible mock server written in Rust. You POST an imposter: a fake service bound to a TCP port, carrying an ordered list of stubs. Each stub is a predicate (“GET /orders/*”) and a response. Your system under test calls the imposter as if it were the real service, and afterwards your test asks Rift what it received.

Some stubs are stateful. A scenario stub only matches when a little state machine is in a given state (requiredScenarioState: "AwaitingPayment") and may move it on (willSetStateTo: "Shipped"). That state belongs to a flow: one test run, one user session, named by a flow_id taken from a header such as X-Flow-Id. Stubs can also cycle through several responses, or proxy to a real upstream once and replay the recording forever (proxyOnce).

A single Rift process serves 20–40k requests per second, so one node usually has enough compute. What one node can't give you is an environment that survives that node dying. The distributed edition exists to meet four requirements. Each one rules out a simpler design:

#RequirementWhat it rules out
R1A config change acknowledged by any node is servable from every node by the time the client sees its 2xx.Fire-and-forget replication; “poll until it converges”.
R2A flow-state change made while serving one request is visible to the very next request, whichever node gets it.Reading local replicas for state that decides which stub matches.
R3Nothing is lost on a full-cluster restart: configs and flow state.Memory-only state; “durable as long as one node survives”.
R4An accepted admin request is never lost, even if the node handling it dies mid-flight.Best-effort forwarding; relying on the client to retry.

And one founding constraint: no mandatory external dependency. No etcd, no Redis, no ZooKeeper. Three Rift binaries behind a load balancer have to be the cluster.

2 · The fleet and the load balancer

The cluster is replicated, not sharded. Every node holds the full imposter set, binds every imposter port, and can answer any mock request. That is what makes the load balancer trivial: it can send anything anywhere, and losing a node loses no configuration.

Blue: mock requests. Dashed grey: the private cluster port (Raft and owner RPCs, every message HMAC-signed).

Traffic reaches an imposter in one of three ways: on its own port (the Mountebank default), on one shared port with stubs separated by a space that matches the flow id, or through the gateway, where the port is carried in the path: /__rift/8080/orders is dispatched in-process to imposter 8080 as /orders. On Kubernetes, where Service ports are fixed, the gateway and the front-door route table are how runtime-minted ports stay reachable.

It is tempting to make the load balancer hash the flow-id header so a flow always lands on “its” node. The design records why this doesn't buy correctness (D-13): the balancer hashes onto its own ring over its own endpoint list. It never computes Rift's ownership function, so the sticky node is the state owner about 1/N of the time, by chance.

Placement is a latency optimization. Ownership is a correctness mechanism. They are computed by different systems and must be assumed to disagree.

3 · What breaks with the obvious design

Start naive: three independent Rift processes behind the balancer, each node copying changes to the others in the background. Step through each scenario to see where it goes wrong.

Scenario 1: config that only one node has seen

A CI job creates an imposter. The balancer sends that request to node B. B saves it, answers 201, and starts copying it to A and C in the background. The test starts immediately.

The client was told “created”, and the very next request failed. That is an R1 violation. Whatever replaces background copying must not answer 201 until every serving node can serve the change.

Scenario 2: state read from a local copy

Now a scenario. Request 1 for flow f lands on node A, matches the Started stub and moves the flow to AwaitingPayment. Request 2 arrives 2 ms later on node B, whose copy of the flow is updated asynchronously.

Nothing errors. The test receives a wrong mock response, which is the one failure a verification tool must never produce. That is an R2 violation: state that decides which stub matches must come from one authoritative place.

Scenario 3: nodes that disagree about who is in the cluster

Suppose we fix scenario 2 by giving each flow one owner, chosen by hashing over the member list. An earlier draft of this design (RFC-001 v2) learned the member list by gossip. During a network blip, two nodes can hold different lists:

Two nodes each believe they own f, and both accept writes. The v2 draft piled up machinery to manage this: ring epochs, settle delays, per-key generations, version-vector merges on heal. The final design removes the disagreement instead of managing it.

4 · Two planes

The fix is to sort state by what goes wrong if two nodes disagree about it, and give each class the cheapest mechanism that makes disagreement impossible.

Control plane

Raft · linearizable · durable · needs a quorum
  • Membership: voters and learners
  • Imposter configs and their enabled bit
  • Front-door route table and its revision
  • Admin intent log and op-id dedup

Changes at human or CI speed. Can afford a quorum round-trip and an fsync per write.

Data plane

per request · no consensus, ever
  • Stateless stub matching: 100% in-process
  • Flow state (scenario FSM, flow KV): one owner per key, chosen by hashing, plus 2 async replicas and a write-ahead tier
  • Request journal: upstream's own, per node
  • proxyOnce claims: a small state machine at the owner

Changes up to tens of thousands of times a second. A stub with no stateful features never touches the cluster.

committed membership (control plane) ──feeds──▶ the ownership ring (data plane)

The arrow between them is the trick. Membership lives in the Raft log, so at any log index every node computes byte-identical membership, and therefore byte-identical owners for every flow. Scenario 3 can't happen. The rule of thumb from chapter 4 of the guide:

Raft carries what you'd expect to survive a restart. The ownership ring carries what a running test mutates.
